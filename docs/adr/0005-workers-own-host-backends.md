# Let one Worker own each host's backends

One Worker per host owns non-overlapping Device Pools, each containing one or more GPUs and at most one Active Runtime. A Pool switches exclusively between managed llama.cpp and ComfyUI processes rather than colocating both; its runtime exposes Execution Slots, with llama.cpp permitting continuous-batched concurrent Attempts and ComfyUI defaulting to one, and Workers never prefetch beyond free Slots. Models stay warm while compatible work exists and for five idle minutes, then yield under incompatible demand or VRAM pressure using backend unload APIs; failed release triggers process termination before the next runtime starts. Operators install backends, drivers, models, and custom nodes, and Workers advertise exact versions and capabilities; automatic installation or distribution is excluded initially.

Worker supports any accelerator accepted by the operator-installed llama.cpp or ComfyUI rather than maintaining a vendor allowlist; device selectors and environment are configuration, vendor telemetry is optional, and process termination is the universal memory-release fallback. Adapters use only managed subprocesses and loopback llama-server HTTP/SSE or ComfyUI HTTP/WebSocket APIs, never C/C++ FFI or Python imports.

Worker TOML defines each Pool's executable, argument vector, environment, state directory, and startup timeout without shell command strings or dynamic reload. Accelerator memory is optional, backend-derived telemetry; unknown memory does not reject work, runtime OOM corrects capability, and successful process termination is the portable release signal.

Workers compute SHA-256 Model Version hashes and cache them atomically by path, size, modification time, and file identity, rehashing on change and rejecting configured expected-hash mismatches. Vendor-specific accelerator tools and exhaustive hardware certification are not required for support.

Backend compatibility is determined by required endpoint probes rather than version allowlists; missing core generation, streaming, progress, result, or cancellation operations makes that backend unready, while missing ComfyUI memory release falls back to process restart. Workers advertise observed versions and probe results without maintaining old-API shims.

Managed children run in a Windows Job Object or Unix process group and are identified durably by PID, start time, and executable identity. Worker startup terminates verified stale children before making a Pool ready, never kills by PID alone, never adopts old processes, and leaves a Pool unready when ownership cannot be proven.
